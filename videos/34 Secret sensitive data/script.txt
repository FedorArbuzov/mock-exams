Where should passwords and tokens live in Kubernetes?

In a Secret, not a ConfigMap. A Secret is built for sensitive data - database passwords, API tokens, TLS keys. It looks like a ConfigMap, but Kubernetes treats it more carefully: it can be encrypted at rest, is kept out of most logs, and access is controlled through RBAC.

But understand the catch. By default Secret values are only base64 encoded, not encrypted, inside etcd. Base64 is not security - anyone who can read the Secret can decode it. Real protection needs encryption at rest enabled and tight RBAC so only the right ServiceAccounts can read it.

What beginners get wrong: committing Secrets to git, or printing them with kubectl get secret dash o yaml in a shared terminal. Also mounting a Secret as env vars, which can leak into crash dumps and child processes - files are often safer.

Practical check: restrict who can get Secrets, prefer volume mounts, and consider an external manager like Vault or a sealed-secrets tool.

Rule to remember: base64 is not encryption - guard Secrets with RBAC.
