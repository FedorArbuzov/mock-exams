Empty logs mean there is no problem, right?

Wrong - and that assumption wastes hours. Logs and Events answer two different questions, and knowing which to read first is a core debugging skill.

Events are Kubernetes talking about orchestration: scheduling, image pulls, probe results, volume mounts, killings. They explain why a Pod is not running yet or why it keeps restarting. Logs are your application talking: the code's own output once the process is actually alive. If the container never started, logs are empty - not because things are fine, but because there was nothing to log.

What beginners get wrong: opening logs first for a Pod stuck in Pending or ImagePullBackOff, finding nothing, and concluding all is well. The answer was in Events the whole time.

Practical rule: if the Pod is not Running - Pending, ContainerCreating, ImagePullBackOff, CreateContainerConfigError - read Events first via kubectl describe. If the Pod is Running or crashing after start, read logs, adding dash dash previous for the last crash.

Rule to remember: not started yet means Events; started then failed means logs.
