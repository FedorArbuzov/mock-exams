# 01. Что такое SRE: история, роль, границы

## Введение: «у нас DevOps, но прод всё равно горит»

Пятница, 23:40. Checkout отдаёт 503, в Slack три канала: `#devops-alerts`, `#backend-oncall`, `#support-escalation`. Дежурный перезапускает Pod'ы, разработчик откатывает релиз, менеджер спрашивает «когда почините». Через неделю та же история — но уже из‑за переполненного диска на Kafka. Команда называет себя **DevOps**, но нет общего ответа на вопросы: *какой уровень недоступности допустим*, *сколько релизов в месяц можно рисковать*, *кто владеет инцидентом*, *что считать «починили»*. 

**Site Reliability Engineering (SRE)** — не набор инструментов и не синоним «админ, который умеет в Kubernetes». Это **инженерный подход к надёжности продуктовых систем**: измеримые цели (SLO), бюджет на ошибки (error budget), дисциплина инцидентов и сознательный обмен между **скоростью изменений** и **стабильностью**. Эта глава задаёт карту местности; детали SLI, инцидентов и ёмкости — в следующих главах.

---

## Откуда взялось SRE

В начале 2000‑х Google столкнулся с масштабом, при котором классическая эксплуатация («админы по серверам») не масштабировалась вместе с продуктами. Команды разработки хотели **часто выкатывать**, а эксплуатация — **не ломать**. Ben Treynor Sloss сформулировал идею: **отдать эксплуатацию продакшена тем же инженерам**, которые проектируют системы — но с **другими KPI**: не «закрыть тикет», а **удержать сервис в SLO**.

Книга *Site Reliability Engineering* (2016, бесплатно от Google) закрепила практики:

- **SLO вместо «должно быть стабильно»**
- **Error budget** как разрешение на риск
- **Toil** — враг, который нужно измерять и сжигать
- **Blameless postmortem** — обучение, а не казнь

Сегодня SRE — **де-факто стандарт** в крупных tech-компаниях; в средних командах — смесь ролей «platform + on-call + SLO-документ».

---

## Определение SRE одной фразой и развёрнуто

**Коротко:** SRE — применение **программной инженерии** к **операционным** проблемам надёжности.

**Развёрнуто:** SRE-команда (или роль) **проектирует** системы так, чтобы они выдерживали реальный мир (отказы, пики, ошибочные релизы), **измеряет** опыт пользователя через SLI/SLO, **реагирует** на отклонения (алерты, инциденты), **учится** (postmortem) и **торгуется** с продуктом: больше фич — меньше запаса надёжности, и наоборот.

| Акцент | Не SRE | SRE |
|--------|--------|-----|
| Цель смены | «потушить пожар» | восстановить **SLO** и убрать класс повторов |
| Метрика успеха | uptime сервера | **доступность пользовательского пути** |
| Релизы | «когда успеем» | в рамках **error budget** |
| Документация | wiki «как перезапустить» | SLO doc + runbook + postmortem |

## SRE vs DevOps vs Platform Engineering

Термины пересекаются; путаница — нормальна.

### DevOps

**DevOps** — культурный и организационный тезис: **сократить стену** между dev и ops, автоматизировать поставку, ответственность «you build it, you run it». DevOps **не задаёт** численно, сколько downtime допустим.

### Platform Engineering

**Platform** (Internal Developer Platform) — **продукт для разработчиков**: CI, кластеры, шаблоны, golden paths. Цель — **скорость и стандартизация**. Platform может **включать** SRE-практики (SLO dashboards, paved road с probes), но может и не иметь error budget policy.

### SRE

**SRE** — **конкретная практика** reliability: SLO, budget, toil ≤50%, инцидент-процесс. В Google SRE часто **отдельная функция** с правом **блокировать** релиз при исчерпанном budget.

```text
                    ┌─────────────────────────────────────┐
                    │         Бизнес-цели продукта         │
                    └─────────────────┬───────────────────┘
                                      │
          ┌───────────────────────────┼───────────────────────────┐
          ▼                           ▼                           ▼
   ┌──────────────┐           ┌──────────────┐           ┌──────────────┐
   │   DevOps     │           │  Platform    │           │     SRE      │
   │ CI/CD, куль- │           │ IDP, шаблоны │           │ SLO, budget, │
   │ тура, автома-│           │ self-service │           │ incidents    │
   │ тизация      │           │              │           │              │
   └──────────────┘           └──────────────┘           └──────────────┘
          │                           │                           │
          └───────────────────────────┴───────────────────────────┘
                              Часто один человек
                              совмещает 2–3 шапки
```

**На практике в mock-exams:** [`gitlab-*`](../gitlab-basic/README.md) + [`gitops-*`](../gitops-basic/README.md) — **поставка**; [`observability-*`](../observability-basic/README.md) — **измерение**; **этот курс SRE** — **как принимать решения**, когда метрика красная.

## Надёжность как свойство продукта

Пользователь не покупает «99,99% uptime Pod'а». Он покупает **возможность оформить заказ**, **увидеть ленту**, **получить платёж**. Надёжность — **вероятность, что путь выполнится приемлемо быстро и правильно**.

| Уровень | Пример «надёжно» | Пример «ненадёжно» |
|---------|------------------|---------------------|
| UX | оплата прошла, чек на почте | списали деньги, заказ «висит» |
| API | 200 за 300 ms p95 | таймауты 30 s |
| Инфра | node NotReady, сервис жив | все реплики в CrashLoop |

SRE смотрит **сверху вниз**: сначала **пользовательский путь**, потом сервисы, потом железо. Алерт «CPU 90%» без связи с путём — **симптом**, не SLI ([глава 06](06-observability-for-sre.md)).

## Типичные роли в SRE-контуре

| Роль | Фокус | Не путать с |
|------|-------|-------------|
| **SRE engineer** | SLO, автоматизация, инциденты, capacity | только «крутить Helm» |
| **Incident Commander (IC)** | координация во время аварии | самый старший по грейду |
| **Tech lead on-call** | глубокая диагностика | единственный, кто пишет в прод |
| **Comms** | статус для бизнеса/поддержки | разработчик в треде |
| **Scribe** | таймлайн, решения | тот, кто «просто записывает» |

Ротация on-call — **не наказание**, а **инвестиция** в обратную связь продукта ([глава 07](07-alerting-on-call.md)).

## Мифы о SRE

| Миф | Реальность |
|-----|------------|
| «SRE = 24/7 дежурство без полномочий» | дежурство — часть роли; полномочия — veto релиза при budget, приоритет reliability work |
| «Нужен 99,999% всему» | избыточная надёжность **дорога**; SLO подбирают под бизнес ([глава 15](15-economics-of-reliability.md)) |
| «SRE заменяет разработчиков» | SRE **партнёр**; код пишут все, ownership сервиса — у команды продукта |
| «Достаточно купить Datadog» | инструмент без SLO = **шум** |
| «Postmortem — для наказания» | цель — **системные** улучшения ([глава 09](09-postmortems.md)) |

## SRE в разных масштабах компании

### Стартап (5–20 инженеров)

Часто **нет отдельной SRE-команды**: основатели + один «дежурный». Имеет смысл **рано**: 1–2 SLO на критичный путь, простой runbook, канал инцидентов. Не нужен 40-страничный process.

### Средний продукт (50–200)

Появляется **platform** + **выделенный on-call** по сервисам. Нужны: **единый шаблон SLO**, weekly review инцидентов, **error budget policy** согласованная с PM.

### Крупный enterprise

Несколько **SRE-подразделений** (foundation vs product-embedded), **центр экспертизы** по инцидентам, **Game Days**, formal PRR ([глава 14](14-production-readiness.md)). Риск — **бюрократия**; противоядие — **toil cap** и автоматизация.

## Заметки для собеседования

- **SRE** = software engineering + operations + **quantified** reliability.
- Отличие от DevOps: **SLO/error budget** как управленческий инструмент.
- **Toil** — ручная, повторяющаяся, без долгосрочной ценности работа; цель — **≤50%** времени (ориентир Google).
- **Blameless** — фокус на системе, не на «кто нажал».
- Надёжность **не максимизируют** — её **торгуют** с cost и velocity.

---

## Резюме

SRE отвечает на вопрос: **«какой уровень ненадёжности мы сознательно принимаем и как управляем им»** — через измерение, бюджет, процессы и инженерию. DevOps и Platform доставляют изменения; SRE делает так, чтобы изменения **не разрушали обещание пользователю**.
