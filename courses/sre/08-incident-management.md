# 08. Инцидент-менеджмент

## Введение: «все в чате, никто не командует»

14:02 — checkout отдаёт 503. В Slack пишут разработчики, DevOps, support, CEO. Кто-то **рестартит** Redis, другой **откатывает** релиз, третий **меняет** лимит в Ingress. Через 20 минут сервис **ожил**, но никто не знает, **что помогло**, и **сколько** пользователей пострадало. В 18:00 повтор — те же гипотезы с нуля.

**Инцидент-менеджмент** — не «починить быстрее любой ценой», а **управляемое восстановление** с ролями, коммуникацией и записью решений. SRE здесь — **процесс и дисциплина**, не обязательно самый глубокий дебаггер.

---

## Инцидент vs проблема vs тикет

| Термин | Определение |
|--------|-------------|
| **Incident** | незапланированное снижение качества сервиса для пользователей |
| **Problem** | корневая причина **класса** сбоев (может жить после закрытия incident) |
| **Ticket** | единица учёта в ITSM; incident может породить много tickets |

Инцидент **закрывают**, когда **восстановлен SLO/сервис**, а не когда «нашли виноватого».

---

## Severity (пример шкалы)

Шкала должна быть **внутренней**, согласованной с support и бизнесом:

| Уровень | Критерий (пример) | Ответ |
|---------|-------------------|-------|
| **P0** | checkout/auth недоступен массово; data loss | немедленный page, IC, comms |
| **P1** | деградация core path, обходной путь есть | page, IC |
| **P2** | важный, но не core; subset users | рабочее время / extended on-call |
| **P3** | internal, cosmetic, workaround | ticket |

**Не путать** с приоритетом баг-трекера. P0 — про **пользователя сейчас**.

Связь с error budget: P0 часто означает **быстрый burn** ([глава 04](04-error-budgets.md)).

## Роли во время инцидента

```text
                    ┌─────────────────┐
                    │ Incident Cmd (IC)│
                    │ координация      │
                    └────────┬────────┘
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
  │ Tech lead   │     │ Comms       │     │ Scribe      │
  │ гипотезы,   │     │ status page │     │ таймлайн,   │
  │ фиксы       │     │ support     │     │ решения     │
  └─────────────┘     └─────────────┘     └─────────────┘
         │
         ▼
  Subject matter experts (DB, network, vendor)
```

| Роль | Делает | Не делает |
|------|--------|-----------|
| **IC** | приоритеты, «стоп/продолжаем», синхронизация | не обязан deepest debug |
| **Tech lead** | гипотезы, kubectl, код, rollback | не пишет в status page |
| **Comms** | шаблоны для support/PR, частота update | не меняет prod |
| **Scribe** | время, действие, результат | не спорит с техникой вместо записи |

**IC** — не «самый старший по грейду», а обученный **фасилитатор**. В маленькой команде один человек совмещает роли — **осознанно**, не хаотично.

## Жизненный цикл инцидента

```text
Detect → Triage → Mitigate → Resolve → Document → Improve
```

| Фаза | Цель | Типичные ошибки |
|------|------|-----------------|
| **Detect** | узнать раньше пользователей | нет симптом-алертов |
| **Triage** | severity, IC, канал | 5 параллельных «фиксов» |
| **Mitigate** | вернуть **сервис** | застрять в root cause |
| **Resolve** | стабильно, мониторинг | закрыть без проверки SLI |
| **Document** | postmortem | «устали, пропустим» |
| **Improve** | action items | actions без owner |

**Mitigate vs fix:** сначала **откат**, **feature flag off**, **traffic shift** — потом разбор **почему**.

## Канал и ритуал

Рекомендуемый минимум:

1. Канал `#inc-YYYYMMDD-shortname` (или PagerDuty incident).
2. Zoom/Meet с **одной** ссылкой в закрепе.
3. **Scribe doc** (Google Doc) — живой таймлайн.
4. Обновление **каждые N минут** (P0: 15–30 min) от comms.

**Шаблон update для leadership:**

```text
[14:35] P0 Checkout errors
Impact: ~15% failed payments EU
Status: mitigating — rollback deploy 4.2.1 in progress
Next update: 15:00
IC: @alice  Tech: @bob
```

## Таймлайн (что писать)

| Время | Событие |
|-------|---------|
| T0 | первый алерт / жалоба support |
| T1 | IC назначен, severity |
| T2 | гипотеза A — проверка |
| T3 | действие (rollback) — результат |
| T4 | SLI восстановлен |
| T5 | incident resolved |

Postmortem строится из **scribe doc**, не из памяти ([глава 09](09-postmortems.md)).

## Эскалация

| Уровень | Когда |
|---------|-------|
| L1 on-call | первые 15 min |
| L2 service owner | нет прогресса |
| L3 platform / vendor | инфра, облако, CDN |
| Executive | P0 длительный, репутационный риск |

**Эскалация** — не признак слабости, а **контракт** ([глава 07](07-alerting-on-call.md)).

---

## Связь с релизами

При инциденте после deploy:

1. **Зафиксировать версию** (image tag, git SHA).
2. **Rollback** — если быстрее, чем forward fix.
3. **Заморозить** релизы при низком budget.

GitOps ([gitops-intermediate](../gitops-intermediate/05-rollback-history.md)) упрощает **revert**; без GitOps — documented rollback runbook.

## War room антипаттерны

| Антипаттерн | Лечение |
|-------------|---------|
| «Все говорят» | IC модерирует, «один голос» |
| Hero debugging | распределить гипотезы |
| Скрытые изменения | все prod actions в scribe |
| Преждевременное «resolved» | критерий: SLI green N min |
| Blame в чате | напомнить blameless policy |

## Метрики процесса (не vanity)

| Метрика | Зачем |
|---------|-------|
| **MTTD** | mean time to detect |
| **MTTR** | mean time to restore service |
| **MTTF** | time to find root cause (после mitigate) |
| Incidents / month по severity | тренд |
| % incidents с postmortem | дисциплина |

**MTTR** для SRE — до **восстановления сервиса**, не до «нашли баг в коде».

---

## Game Day и учения

**Game Day** — запланированный инцидент (отключить AZ, убить dependency) с **реальным** процессом IC/comms. Цель — тренировать **людей и runbook**, не «поймать» дежурного.

Отличие от chaos engineering: chaos — **система**; Game Day — **организация**.

## Резюме

Инцидент — **проект на часы**: роли, канал, таймлайн, восстановление **опыта пользователя**, потом обучение. Без IC и scribe вы платите **повторными** 40-минутными хаосами.
