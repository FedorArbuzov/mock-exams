# 03. Конвей и топология команд

## Введение

Пять команд и три микросервиса с общей БД — архитектура отразила **оргструктуру**: все ходят в одну схему, потому что «так проще». **Закон Конвея** и **Team Topologies** связывают границы кода с границами ответственности.

---

## Закон Конвея

> Организации проектируют системы, копирующие структуру коммуникации организации.

| Оргструктура | Архитектура «по умолчанию» |
|--------------|----------------------------|
| Фронт / бэк / DBA | слоистый монолит |
| По фичам (команды A, B) | сервисы по фичам (если дали автономию) |
| «Общий отдел интеграций» | ESB, god service |

**Reverse Conway:** спроектируйте **желаемую** топологию команд → затем границы сервисов ([devops-culture/06](../devops-culture/06-reverse-conway.md)).

---

## Team Topologies (4 типа)

| Тип | Роль |
|-----|------|
| **Stream-aligned** | поток ценности (продукт, домен) |
| **Platform** | self-service infra (K8s, CI, observability) |
| **Enabling** | временно помогает освоить практику |
| **Complicated-subsystem** | ML, billing engine — редкий deep expertise |

Каждый **микросервис** (или группа тесно связанных) должен иметь **явного владельца** — stream-aligned команда.

---

## Two-pizza team и cognitive load

| Правило | Практика |
|---------|----------|
| Владение 2–3 сервисами max | иначе on-call ад |
| On-call на владельца сервиса | не «общий дежурный бэкенд» |
| Platform снимает toil | не заставлять stream team писать Helm с нуля |

---

## Interaction modes

| Режим | Когда |
|-------|-------|
| **Collaboration** | discovery, новый продукт |
| **X-as-a-Service** | стабильная platform API |
| **Facilitating** | enabling помогает stream |

Микросервисы между stream-командами → контракт **X-as-a-Service** (версионированный API/events), не бесконечные созвоны.

---

## Владение и «shared» сервисы

| Плохо | Лучше |
|-------|-------|
| «Общий» Auth без владельца | Platform identity или выделенная команда |
| Каждый патчит logging | Platform observability |
| Rotation «все всё чинят» | runbook + владелец домена |

## Подзадачи

**Время:** ~45–55 мин.

### 3.1 Текущая карта (15 мин)

Для продукта из гл.01: сколько команд? Кто деплоит что? Кто в on-call? Таблица team × сервис/модуль.

### 3.2 Conway diagnosis (10 мин)

Одна проблема архитектуры, которая **отражает** текущую оргструктуру (пример: «общая БД, потому что одна DBA-команда»).

### 3.3 Целевая топология (15 мин)

Назначьте stream-aligned команды на bounded contexts из гл.02. Укажите одну platform и одну enabling (если нужна).

### 3.4 Interaction mode (10 мин)

Для связи «Orders → Payment» выберите режим и опишите **контракт** (sync API vs event + SLA ответа).

### 3.5 On-call (5 мин)

Кто дежурит по Payment в целевой модели? Что эскалируется в platform?

---

## Резюме

Микросервис без владельца команды → **брошенный** сервис. Reverse Conway: сначала команды и режимы взаимодействия, потом репозитории.
