# 05. Закон Конвея и архитектура

## Введение

1968 — Melvin Conway: **организации проектируют системы, копирующие структуру коммуникации**. Monolith с 80 разработчиками в одном open space — один deployable. Три silo «frontend / backend / DBA» — три слоя с **жёсткими** API и медленными изменениями.

---

## Формулировка для инженеров

```text
Архитектура ≈ f(кто с кем разговаривает каждый день)
```

Не **технология** диктует границы первично — **социальная структура**. Потом границы **цементируются** в коде.

---

## Примеры

| Организация | Типичная система |
|-------------|------------------|
| 4 команды по слоям (UI, API, DB, ops) | 3-tier, shared DB, «API gateway как стена» |
| 6 команд по продуктовым фичам | 6 сервисов (или 6 модулей) |
| 1 platform + 8 squads | общий K8s, разные namespaces / repos |
| Outsourced QA отдельно | «throw over the wall», долгий release |

---

## Связь с микросервисами

Микросервисы **работают**, когда:

- **команды** автономны (владеют сервисом + данными или чётким контрактом);
- **интерфейсы** стабильны;
- **операционная** зрелость есть (observability, [sre](../sre/README.md)).

Микросервисы **ломаются**, когда:

- одна команда на 40 сервисов;
- distributed monolith — всегда joint deploy;
- нет platform — каждый squad поднимает свой Kafka.

---

## Communication paths

Чем **больше** людей должны согласовать изменение, тем **выше** latency и **ниже** эксперименты.

```text
Squad A ──► Squad B ──► Ops ──► Security ──► Prod
         (4 handoffs = lead time взрывается)
```
