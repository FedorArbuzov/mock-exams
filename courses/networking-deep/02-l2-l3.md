# 02. L2–L3: ARP, VLAN, CIDR и проектирование адресов

## Введение

«Пинг по IP не идёт, но по имени вроде работает» — иногда это **разные подсети** и ARP. «В Docker всё в одной сети» — но за NAT другой **L3-мир**. Эта глава углубляет [linux-intermediate/01](../linux-intermediate/01-tcp-ip.md) и связывает с [bare-metal/07](../bare-metal/07-host-networking.md).

---

## ARP и соседи

В одной broadcast-домене (одна L2-сеть / VLAN) хост узнаёт MAC по ARP:

```bash
ip neigh show
arp -n
```

| Состояние | Смысл |
|-----------|--------|
| `REACHABLE` | недавно отвечал |
| `STALE` | кэш, может обновиться |
| `FAILED` | нет ответа — кабель, VLAN, wrong subnet |

**Proxy ARP** — маршрутизатор отвечает ARP за другую подсеть (встречается в VPN и некоторых cloud NIC).

---

## VLAN: логические L2-сети

802.1Q tag в кадре → один физический линк, много broadcast-доменов.

```text
bond0.100  → VLAN 100 (management)
bond0.200  → VLAN 200 (storage)
bond0.300  → VLAN 300 (VM traffic)
```

В AWS **нет классического VLAN** внутри VPC для клиента — изоляция через **VPC + SG**. VLAN остаётся релевантным для **on-prem**, **bare metal**, **Direct Connect**.

## CIDR: проектирование, не «взять /24»

### Правила планирования

1. **Суммаризация** — смежные `/24` можно агрегировать в `/23`, `/22` для таблиц маршрутов.
2. **Запас** — в VPC `/16` не занимайте все `/24` подряд; оставьте блоки под EKS, Lambda ENI, RDS.
3. **Перекрытия** — VPN/peering **ломаются**, если `10.0.0.0/16` в офисе и в VPC совпадают.
4. **Зарезервированные** в AWS subnet: первые 4 адреса + broadcast — см. [aws-intermediate/01](../aws-intermediate/01-vpc-custom.md).

### Пример плана (production sketch)

```text
10.0.0.0/16     production VPC
  10.0.0.0/20   public (4x /22 по AZ — гибче чем 4x /24)
  10.0.16.0/20  private app
  10.0.32.0/20  private data
  10.0.48.0/20  reserved (EKS secondary CIDR позже)

172.16.0.0/16   staging — другой диапазон, нет peering conflict
```

### Учебный стенд deploy/linux

| Хост | IP | Подсеть |
|------|-----|---------|
| lab | 172.28.0.10/24 | 172.28.0.0/24 |
| srv1 | 172.28.0.11/24 | та же L2 (Docker bridge) |

В Docker все «хосты» часто в **одном L2** — ARP простой; для симуляции **двух подсетей** в лабе 15 используют namespace или вторую сеть compose.

## Таблица маршрутов (введение)

```bash
ip route show
ip route get 8.8.8.8
```

| Маршрут | Поведение |
|---------|-----------|
| `172.28.0.0/24 dev eth0` | connected — напрямую |
| `default via 172.28.0.1` | всё остальное на шлюз |
| `10.0.10.0/24 via 10.0.1.5` | static к другой подсети |

**Main table** vs **policy routing** — в [главе 05](05-routing.md).

## ICMP и «ping не доказательство»

- Firewall может дропать **ICMP**, но пропускать **TCP/443**.
- `ping` успешен с **mgmt** VLAN, но приложение в **app** VLAN недоступно.

Для SLA пути пользователя проверяйте **тот же L4**, что и клиент: `curl`, `nc`, synthetic check.

## Резюме

L2 — **кто в одном broadcast-домене** (ARP, VLAN). L3 — **куда форвардить** (CIDR, маршруты). Плохой адресный план дороже любого бага в приложении — исправляется миграцией и downtime.
