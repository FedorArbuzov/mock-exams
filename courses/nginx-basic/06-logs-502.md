# 06. access/error log и диагностика 502

## Введение: клиент видит 502 — кто виноват?

**502 Bad Gateway** означает: **edge nginx принял** запрос, обратился к **upstream**, но не получил корректный HTTP-ответ. Сам nginx при этом обычно **жив** — `curl http://localhost:8080/` на edge OK, а `curl .../api/health` — 502.

В [linux-intermediate/13](../linux-intermediate/13-nginx.md) разобран тот же симптом на VM. На стенде логи edge лежат в **`deploy/nginx/logs/`** на хосте и дублируются в `docker compose logs edge`. Лаба с намеренным падением api — [07](07-lab-502-debug.md).

## Что вы узнаете

- Формат **access.log** и уровни **error.log**.
- Типичные строки error.log при 502.
- Порядок диагностики: edge → upstream → compose.
- Отличие 502 от 404 и 504.

## Два журнала

| Файл | Содержимое | Когда смотреть |
|------|------------|----------------|
| `access.log` | каждый запрос: IP, статус, URI, bytes | кто звонил, сколько 5xx |
| `error.log` | сбои upstream, rewrite, permission | **почему** 502 |

Формат access задан в [`nginx.conf`](../../deploy/nginx/config/nginx.conf):

```nginx
log_format main '$remote_addr - ... "$request" $status ...';
access_log /var/log/nginx/access.log main;
error_log  /var/log/nginx/error.log warn;
```

Просмотр с хоста:

```bash
cd deploy/nginx
tail -f logs/access.log
tail -f logs/error.log
```

Или из compose:

```bash
docker compose logs -f edge
```

## Коды ответа: кто их отдаёт

| Код | Кто отвечает | Типичная причина на стенде |
|-----|--------------|----------------------------|
| 404 | nginx или app | неверный path / proxy_pass |
| 502 | **nginx edge** | api down, connection refused |
| 504 | **nginx edge** | upstream timeout |
| 429 | nginx | rate limit (intermediate, `/login`) |

**404** после proxy_pass часто означает «backend жив, path не тот». **502** — «до backend не достучались или он упал».

## Типичные строки error.log

```text
connect() failed (111: Connection refused) while connecting to upstream
upstream timed out (110: Connection timed out) while reading response header
no live upstreams while connecting to upstream
```

| Строка | Интерпретация | Первый шаг |
|--------|---------------|------------|
| Connection refused | порт не слушает | `docker compose ps api` |
| timed out | app завис / сеть | логи api, `proxy_read_timeout` |
| no live upstreams | все серверы в upstream помечены down | [глава 08](08-upstream.md) |

## Алгоритм диагностики (5 шагов)

1. **Воспроизвести:** `curl -v http://localhost:8080/api/health`
2. **access.log:** статус 502, upstream_addr (если расширить log_format)
3. **error.log:** последние 20 строк в момент запроса
4. **С edge в сеть:** `docker compose exec mock-nginx-edge wget -qO- http://api:8080/health`
5. **Состояние контейнера:** `docker compose ps`, `docker compose logs api --tail 30`

Если шаг 4 **OK**, а с хоста через edge **502** — смотрите **конфиг** location (редко). Если шаг 4 **fail** — проблема **api**, не «интернет».

## Race при старте compose

Web в [containers-basic](../containers-basic/10-compose-multi-service.md) ждёт `service_healthy` api. В `deploy/nginx` у edge только `depends_on` без condition — edge может стартовать раньше api. Симптом: первые секунды **502**, потом 200. Решение в проде: healthcheck + wait script или retry в smoke.

## Уровни error_log

```nginx
error_log /var/log/nginx/error.log warn;
```

| Уровень | Объём |
|---------|-------|
| `warn` | ошибки upstream, deprecated |
| `info` | больше деталей (лабы) |
| `debug` | очень шумно, только кратко |

Для лабы 07 достаточно `warn`.

## Расширение access log (идея)

В проде добавляют `$upstream_status`, `$upstream_addr`, `$request_time`:

```nginx
log_format upstream '$remote_addr "$request" $status '
                    'ups=$upstream_status addr=$upstream_addr rt=$request_time';
```

На стенде basic можно добавить в отдельный файл `conf.d/99-debug-log.conf` для финального проекта.

## Связь с containers-basic

502 на `localhost:8088/api/*` в compose-стеке — те же шаги: `docker compose logs api`, healthcheck, [README deploy/containers](../../deploy/containers/README.md).

## Типичные ошибки

| Ошибка | Результат |
|--------|-----------|
| Смотреть только access.log | не видно «connection refused» |
| Чинить edge при мёртвом api | бесполезный reload |
| Путать 502 и 404 proxy_pass | разные лечения |

## В продакшене

- access/error в **Loki/ELK**, алерт на рост 5xx.
- Synthetic probe снаружи + изнутри кластера.
- Runbook: «502 на /api» → upstream health → deploy rollback.

## Резюме

**502** — диагностика с **error.log** и проверки upstream **с той же машины, что edge** (`docker compose exec mock-nginx-edge ...`). **404** на API чаще конфиг URI. Следующая лаба — выключить api и прочитать логи.
