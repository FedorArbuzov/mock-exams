# 00. Окружение Docker-лаб

## Зачем отдельный стенд

На работе вы чаще всего попадаете на Linux через **SSH** в уже настроенный сервер или через **контейнер** в CI. Редко нужно «с нуля» ставить ОС на ноутбук — но **уметь ориентироваться в системе** нужно всегда: права, сервисы, сеть, логи.

Этот курс даёт ту же привычку: **одна и та же лабораторная среда** для всех уроков `linux-basic`, `linux-intermediate` и части `linux-advanced`. Вы поднимаете её одной командой Docker Compose — без отдельной VM, без dual boot и без обязательного WSL (хотя на Windows Docker Desktop как раз использует WSL2 под капотом).

Полное описание стенда — в [`deploy/linux`](../../deploy/linux/README.md). Если что-то не стартует, начните оттуда: там troubleshooting, порты и учётные данные.

## Топология — кто с кем говорит

Представьте мини-ЦОД из пяти «машин» в одной Docker-сети `172.28.0.0/24`. Вы почти всегда заходите в **lab** — это ваша «рабочая станция админа». Остальные контейнеры играют роли серверов, к которым вы ходите по SSH, HTTP или DNS.

```text
                    ┌─────────────┐
   вы ──exec──►     │ lab         │  172.28.0.10
                    └──────┬──────┘
           SSH / HTTP     │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
    srv1 (.11)      srv2 (.12)       web (.20)
         │                                 │
         └──────────── DNS (.53) ─────────┘
```

| Контейнер | IP | Роль в курсе |
|-----------|-----|----------------|
| **lab** | 172.28.0.10 | Точка входа: bash, правки конфигов, запуск клиентов |
| **srv1** | 172.28.0.11 | «Прод-подобный» хост: Apache, Postfix, LVM-лабы |
| **srv2** | 172.28.0.12 | Второй узел: пары srv1/srv2, keepalived (advanced) |
| **web** | 172.28.0.20 | Nginx, TLS, reverse proxy |
| **dns** | 172.28.0.53 | BIND, зона `lab.local` |

Имена вроде `srv1.lab.local` появятся в intermediate — когда настроите резолвинг через dns.

## Запуск с нуля

Из корня репозитория (или из каталога, где лежит `deploy/linux`):

```bash
cd deploy/linux
docker compose build
docker compose up -d
docker compose ps
```

**Первый запуск** может занять несколько минут: скачивается образ, ставятся пакеты, поднимается **systemd** внутри контейнеров. Подождите 30–60 секунд и проверьте `ps` ещё раз — все сервисы должны быть `Up`, не `Restarting`.

Если `build` падает с ошибкой про daemon — на Windows/macOS **запустите Docker Desktop** и дождитесь зелёного статуса «Engine running».

## Как зайти в лаб

Основной способ — интерактивный shell в контейнере lab:

```bash
docker compose exec lab bash
```

Внутри вы можете быть **root** или пользователь **course** — в разных уроках явно скажут, от кого выполнять команды. Для привилегированных операций используйте `sudo` (пароль ниже).

Учебные учётные данные **только для стенда**, не используйте такие пароли в проде:

| Пользователь | Пароль | Зачем |
|--------------|--------|--------|
| course | course | SSH на srv1/srv2, sudo в лабах |
| root | (часто без пароля в контейнере) | Полный доступ внутри контейнера |

## Быстрая проверка «всё живо»

Выполните из хоста (после `exec` в lab — изнутри lab):

```bash
ping -c2 172.28.0.11
ssh course@172.28.0.11 hostname
```

При **первом** SSH OpenSSH спросит про fingerprint — в учебной среде ответьте `yes`. Если `Connection refused` — подождите ещё минуту: sshd в srv1 мог ещё не стартовать.

Удобная привычка на весь курс: перед лабой один раз `ping` или `ssh` до нужного IP — не тратить время на отладку «сломанного» задания, когда просто не поднялась сеть.

## Ограничения Docker — честно ожидания

Стенд **намеренно** приближен к реальному серверу (systemd, ssh, apt, nginx, LVM на loop-дисках), но это не железо:

| В стенде нормально работает | Чего не ждите |
|------------------------------|--------------|
| systemd, unit-файлы, journal | Настоящий RAID и hot-swap дисков |
| ssh, cron, firewall (nft/ufw) | Загрузчик GRUB и PXE «как в ЦОД» |
| LVM на файлах-заглушках | Поведение драйверов железа |
| Сеть между контейнерами | 1:1 копия latency/MTU продакшена |

Темы **bare metal** (BMC, стойка, PXE, аппаратный RAID) — отдельный трек [`bare-metal`](../bare-metal/README.md). Там можно читать теорию без обязательных лаб в Docker.

## Сброс, когда «всё сломали»

Эксперименты с `chmod`, firewall или `/etc/ssh/sshd_config` иногда оставляют систему в странном состоянии. Самый быстрый откат:

```bash
cd deploy/linux
docker compose down -v
docker compose up -d --build
```

Флаг `-v` удаляет тома — **все ваши файлы внутри контейнеров** пропадут. Для учебного стенда это нормально; для своих заметок храните скрипты в репозитории на хосте, не только в `/tmp` контейнера.
