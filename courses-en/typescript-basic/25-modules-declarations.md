# 25. Modules, ESM and `.d.ts`: ambient types

## Scenario from work

You add the `left-pad` library without types — the IDE is silent, `tsc` complains. A colleague added `declare module "left-pad"` in `global.d.ts`, and the error disappeared. A month later the library's API changed — the types **lie**, the runtime crashes. Second case: `"type": "module"` in package.json, but an old config with `"module": "CommonJS"` — `require` and `import` got mixed in `dist`. Third: importing an SVG as a URL in Vite — you need an ambient declaration.

TypeScript understands **modules** (files with import/export) and **declaration files** (`.d.ts`) — descriptions of types **without** JS emit.

## What you'll learn

- ESM in TypeScript: `import` / `export`, `import type`
- The difference between `.ts`, `.mts`, `.cts` (overview)
- `.d.ts` files: declaration emit and hand-written
- Ambient declarations: `declare module`, `declare global`
- Types for non-TS assets (`.json`, `.css`)
- `@types/*` and DefinitelyTyped

## ESM in TypeScript

Source:

```typescript
// src/format.ts
export function formatPrice(cents: number): string {
  return `$${(cents / 100).toFixed(2)}`;
}

export type Currency = "USD" | "EUR";
```

Consumer:

```typescript
import { formatPrice, type Currency } from "./format.js";
```

### `import type` — types only

```typescript
import type { Task } from "./task.js";
import { createTask, type CreateTaskOptions } from "./task.js";
```

With `importsNotUsedAsValues: "error"` (or `verbatimModuleSyntax: true`), a mixed import is split: value separately, type separately. A **type-only import is erased** at compile time — it won't be in the `.js`.

### Re-exporting types

```typescript
export type { Task, TaskStatus } from "./task.js";
export { createTask } from "./task.js";
```

Barrel `index.ts`:

```typescript
export * from "./task.js";
export * from "./store.js";
```

Be careful with `export *` — see [javascript-basic/30-es-modules.md](../javascript-basic/30-es-modules.md).

## Config for Node ESM

`package.json`:

```json
{
  "name": "task-cli",
  "type": "module",
  "scripts": {
    "build": "tsc",
    "start": "node dist/cli.js"
  }
}
```

`tsconfig.json`:

```json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "declaration": true,
    "declarationMap": true,
    "outDir": "dist",
    "rootDir": "src"
  }
}
```

After `tsc`:

```text
dist/
  format.js
  format.d.ts
  format.d.ts.map
```

`.d.ts.map` helps the IDE jump to the `.ts` from a library's types.

## What `.d.ts` is

A **declaration file** — types only, no implementation:

```typescript
// dist/format.d.ts (generated by tsc)
export declare function formatPrice(cents: number): string;
export type Currency = "USD" | "EUR";
```

Hand-written for a JS library in the repository:

```typescript
// types/legacy-cart.d.ts
export interface CartItem {
  sku: string;
  qty: number;
}

export function addToCart(item: CartItem): void;
```

Linked via `include` in tsconfig or `"types"` in the library's package.json.

## `@types/*` and DefinitelyTyped

For popular JS packages, types are published separately:

```bash
npm install -D @types/node @types/express
```

TypeScript automatically picks up `@types` from `node_modules/@types`.

If there are no types — three paths:

1. Write your own `.d.ts` (locally or as a PR to DefinitelyTyped).
2. A `declare module "pkg"` stub (temporarily).
3. Switch to a fork/alternative that has types.

## Ambient module declaration

```typescript
// src/types/shims.d.ts
declare module "untyped-logger" {
  export function log(msg: string): void;
  export function logError(msg: string, err?: unknown): void;
}
```

A file **without** a top-level `import`/`export` is **ambient** (global for the project). If you add `export {}`, the file becomes a module and the scope is narrower.

**Risk:** a stub doesn't check the real API. Prefer types from npm or Zod at runtime.

---

## `declare global`

Extending global objects:

```typescript
// env.d.ts
export {};

declare global {
  namespace NodeJS {
    interface ProcessEnv {
      API_BASE: string;
      NODE_ENV: "development" | "production" | "test";
    }
  }
}
```

`export {}` is required so the file is a module and `declare global` works.

For the browser:

```typescript
interface Window {
  __APP_VERSION__: string;
}
```

## Non-code imports (Vite / bundler)

```typescript
// vite-env.d.ts
/// <reference types="vite/client" />

declare module "*.svg" {
  const src: string;
  export default src;
}

declare module "*.css" {
  const classes: Record<string, string>;
  export default classes;
}
```

`/// <reference types="..." />` — a triple-slash directive that links a package's types.

### JSON modules

```json
// tsconfig
{
  "compilerOptions": {
    "resolveJsonModule": true
  }
}
```

```typescript
import data from "./data/products.json" with { type: "json" };
// or resolveJsonModule + import without assert in older TS
```

## `.ts` vs `.mts` vs `.cts`

| Extension | Format under NodeNext |
|------------|---------------------|
| `.ts` | from `"type"` in package.json |
| `.mts` | always ESM |
| `.cts` | always CommonJS |

In the mock-exams course, `.ts` + `"type": "module"` is enough.

## Publishing a typed npm package

The library's `package.json`:

```json
{
  "name": "@shop/task-types",
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  }
}
```

The consumer gets the types without a separate `@types`.

## Common mistakes

1. **`declare module` with the wrong signature** — a false sense of security.

2. **An ambient file with `import` but without `export {}`** — unexpected global scope.

3. **Forgot `.js` in imports** with NodeNext.

4. **`import type` used as a value** — TS1361.

5. **Duplicate `@types/foo` and built-in types** — a version conflict.

6. **Didn't enable `declaration`** — library consumers don't see the API.

---

## Summary

TypeScript modules = ESM/CJS + type-only imports. `.d.ts` describes JS for the compiler; `tsc` generates them from `.ts` or you write them by hand. Ambient `declare module` is a last resort for untyped deps. `declare global` extends the environment. For Node ESM: NodeNext + `.js` extensions + `"type": "module"`.
