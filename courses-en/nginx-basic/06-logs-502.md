# 06. access/error log and 502 diagnostics

## Intro: the client sees a 502 — who's to blame?

**502 Bad Gateway** means: the **edge nginx accepted** the request, reached out to the **upstream**, but did not get a valid HTTP response. nginx itself is usually **alive** at that point — `curl http://localhost:8080/` on the edge is OK, while `curl .../api/health` is a 502.

[linux-intermediate/13](../linux-intermediate/13-nginx.md) covers the same symptom on a VM. On the stand the edge logs live in **`deploy/nginx/logs/`** on the host and are duplicated in `docker compose logs edge`. The lab with an intentional api failure is [07](07-lab-502-debug.md).

## What you'll learn

- The **access.log** format and the **error.log** levels.
- Typical error.log lines on a 502.
- The diagnostic order: edge → upstream → compose.
- The difference between 502, 404, and 504.

## Two journals

| File | Contents | When to look |
|------|------------|----------------|
| `access.log` | every request: IP, status, URI, bytes | who called, how many 5xx |
| `error.log` | upstream, rewrite, permission failures | **why** the 502 |

The access format is defined in [`nginx.conf`](../../deploy/nginx/config/nginx.conf):

```nginx
log_format main '$remote_addr - ... "$request" $status ...';
access_log /var/log/nginx/access.log main;
error_log  /var/log/nginx/error.log warn;
```

Viewing from the host:

```bash
cd deploy/nginx
tail -f logs/access.log
tail -f logs/error.log
```

Or from compose:

```bash
docker compose logs -f edge
```

## Response codes: who returns them

| Code | Who responds | Typical cause on the stand |
|-----|--------------|----------------------------|
| 404 | nginx or app | wrong path / proxy_pass |
| 502 | **nginx edge** | api down, connection refused |
| 504 | **nginx edge** | upstream timeout |
| 429 | nginx | rate limit (intermediate, `/login`) |

A **404** after proxy_pass often means "the backend is alive, the path is wrong". A **502** means "couldn't reach the backend or it went down".

## Typical error.log lines

```text
connect() failed (111: Connection refused) while connecting to upstream
upstream timed out (110: Connection timed out) while reading response header
no live upstreams while connecting to upstream
```

| Line | Interpretation | First step |
|--------|---------------|------------|
| Connection refused | the port isn't listening | `docker compose ps api` |
| timed out | app hung / network | api logs, `proxy_read_timeout` |
| no live upstreams | all servers in the upstream marked down | [chapter 08](08-upstream.md) |

## Diagnostic algorithm (5 steps)

1. **Reproduce:** `curl -v http://localhost:8080/api/health`
2. **access.log:** status 502, upstream_addr (if you extend the log_format)
3. **error.log:** the last 20 lines at the moment of the request
4. **From the edge into the network:** `docker compose exec mock-nginx-edge wget -qO- http://api:8080/health`
5. **Container state:** `docker compose ps`, `docker compose logs api --tail 30`

If step 4 is **OK** but you get a **502** through the edge from the host — look at the location **config** (rare). If step 4 **fails** — the problem is the **api**, not "the internet".

## Race on compose startup

The web in [containers-basic](../containers-basic/10-compose-multi-service.md) waits for `service_healthy` on the api. In `deploy/nginx` the edge only has `depends_on` without a condition — the edge may start before the api. Symptom: **502** for the first few seconds, then 200. The production fix: healthcheck + a wait script or a retry in smoke.

## error_log levels

```nginx
error_log /var/log/nginx/error.log warn;
```

| Level | Volume |
|---------|-------|
| `warn` | upstream errors, deprecated |
| `info` | more detail (labs) |
| `debug` | very noisy, only briefly |

For lab 07 `warn` is enough.

## Extending the access log (idea)

In production people add `$upstream_status`, `$upstream_addr`, `$request_time`:

```nginx
log_format upstream '$remote_addr "$request" $status '
                    'ups=$upstream_status addr=$upstream_addr rt=$request_time';
```

On the basic stand you can add this in a separate file `conf.d/99-debug-log.conf` for the final project.

## Connection to containers-basic

A 502 on `localhost:8088/api/*` in the compose stack — the same steps: `docker compose logs api`, healthcheck, [README deploy/containers](../../deploy/containers/README.md).

## Common mistakes

| Mistake | Result |
|--------|-----------|
| Looking only at access.log | you don't see "connection refused" |
| Fixing the edge while the api is dead | a useless reload |
| Confusing 502 and 404 proxy_pass | different remedies |

## In production

- access/error in **Loki/ELK**, an alert on rising 5xx.
- A synthetic probe from the outside + from inside the cluster.
- Runbook: "502 on /api" → upstream health → deploy rollback.

## Summary

A **502** is diagnosed with the **error.log** and by checking the upstream **from the same machine as the edge** (`docker compose exec mock-nginx-edge ...`). A **404** on the API is more often a URI config. The next lab — turn off the api and read the logs.

- Where do the edge logs live on the host?
