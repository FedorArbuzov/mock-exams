# 09. Major upgrade: pg_upgrade

## Real-world scenario

Postgres 16 reaches EOL in 6 months. The team plans "a night of downtime + pg_dump of the whole 800 GB DB" — 14 hours, with the risk of not fitting the window. The alternative: **pg_upgrade** in 2 hours, or **logical replication** with a 15-minute cutover. The wrong choice — a downtime SLA breach and no rollback.

A major upgrade (16→17) ≠ a minor patch. This chapter is about strategies and `pg_upgrade`; managed — blue/green ([13-cloud-k8s](13-cloud-k8s.md)).

## Strategies

| Method | Downtime | Complexity | Rollback |
|-------|----------|-----------|-------|
| **pg_dump / restore** | Long (proportional to size) | Low | New cluster, old one alive |
| **pg_upgrade** | Shorter (in-place data dir) | Medium | Harder with `--link` |
| **Logical replication** | Minimal cutover | High | A dual-write period is possible |

```text
pg_dump:     old PG ──export──> SQL/custom ──import──> new PG
pg_upgrade:  old PGDATA ──migrate pages──> new PGDATA (same host)
logical:     old primary ──pub/sub──> new cluster ──cutover──>
```

## pg_upgrade

```bash
pg_upgrade \
  --old-datadir=/var/lib/postgresql/16/data \
  --new-datadir=/var/lib/postgresql/17/data \
  --old-bindir=/usr/lib/postgresql/16/bin \
  --new-bindir=/usr/lib/postgresql/17/bin \
  --check
```

Don't start the production window without `--check`.

| Flag | Meaning |
|------|-------|
| `--check` | Checks only, no changes |
| `--link` | Hard link data files — **fast**, the old PGDATA can't be used as a rollback |
| `-j 4` | Parallel for dumping globals/statistics |
| `--clone` | APFS/reflink where supported |

After a successful upgrade:

```bash
./analyze_new_cluster.sh   # generated by pg_upgrade
./delete_old_cluster.sh    # only when you're sure
```

## Pre-upgrade checklist

1. **Read the release notes** for PG 17 — breaking changes, removed features.
2. `pg_dumpall --globals-only` — roles, tablespaces.
3. A list of extensions + version compatibility on PG 17.
4. `pg_upgrade --check` on a copy of PGDATA.
5. Disk space: without `--link` — ~the full cluster size; with `--link` — less, but rollback is hard.
6. Maintenance window + communication.
7. Rollback plan: snapshot the volume / leave the old cluster untouched until verify.
8. Application: driver, ORM, SQL compatibility.

## After the upgrade

```sql
ANALYZE;
-- when the collation provider changes in a major:
-- REINDEX DATABASE ...;
SELECT extname, extversion FROM pg_extension;
ALTER EXTENSION pg_stat_statements UPDATE;
```

Monitor for 24–48h: query plans, errors, replication lag.

## Logical replication path

For near-zero downtime:

1. A new PG 17 cluster.
2. `CREATE PUBLICATION` on old (wal_level=logical).
3. `CREATE SUBSCRIPTION` on new, catchup.
4. Cutover: stop writes, lag=0, redirect app, drop old.

More: [intermediate/07-logical-replication](../postgresql-intermediate/07-logical-replication.md).

## Managed (RDS / Aurora)

AWS **blue/green deployment**: green on the new version, replication, switchover. You don't run `pg_upgrade` manually — but you do **test** on green before the switch.

## Common mistakes

1. `pg_upgrade --link` without understanding it — no file-level rollback.
2. The `postgis` extension is incompatible — the upgrade fails in the window.
3. Forgot `ANALYZE` — "everything is slow after the upgrade".
4. Cutover of logical replication without checking sequences.
