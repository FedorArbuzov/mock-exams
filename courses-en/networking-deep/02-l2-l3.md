# 02. L2–L3: ARP, VLAN, CIDR, and address design

## Intro

"Ping by IP doesn't work, but by name it seems to" — sometimes these are **different subnets** and ARP. "In Docker everything is on one network" — but behind NAT there's a different **L3 world**. This chapter goes deeper than [linux-intermediate/01](../linux-intermediate/01-tcp-ip.md) and connects to [bare-metal/07](../bare-metal/07-host-networking.md).

---

## ARP and neighbors

Within a single broadcast domain (one L2 network / VLAN) a host learns the MAC via ARP:

```bash
ip neigh show
arp -n
```

| State | Meaning |
|-----------|--------|
| `REACHABLE` | replied recently |
| `STALE` | cached, may be refreshed |
| `FAILED` | no reply — cable, VLAN, wrong subnet |

**Proxy ARP** — a router replies to ARP on behalf of another subnet (seen in VPNs and some cloud NICs).

---

## VLAN: logical L2 networks

An 802.1Q tag in the frame → one physical link, many broadcast domains.

```text
bond0.100  → VLAN 100 (management)
bond0.200  → VLAN 200 (storage)
bond0.300  → VLAN 300 (VM traffic)
```

In AWS there is **no classic VLAN** inside a VPC for the customer — isolation is via **VPC + SG**. VLAN remains relevant for **on-prem**, **bare metal**, and **Direct Connect**.

## CIDR: design, not "just take a /24"

### Planning rules

1. **Summarization** — adjacent `/24`s can be aggregated into `/23`, `/22` for route tables.
2. **Headroom** — in a `/16` VPC, don't allocate all your `/24`s back-to-back; leave blocks for EKS, Lambda ENIs, RDS.
3. **Overlaps** — VPN/peering **breaks** if `10.0.0.0/16` matches in the office and in the VPC.
4. **Reserved** addresses in an AWS subnet: the first 4 addresses + broadcast — see [aws-intermediate/01](../aws-intermediate/01-vpc-custom.md).

### Example plan (production sketch)

```text
10.0.0.0/16     production VPC
  10.0.0.0/20   public (4x /22 per AZ — more flexible than 4x /24)
  10.0.16.0/20  private app
  10.0.32.0/20  private data
  10.0.48.0/20  reserved (EKS secondary CIDR later)

172.16.0.0/16   staging — a different range, no peering conflict
```

### The deploy/linux teaching sandbox

| Host | IP | Subnet |
|------|-----|---------|
| lab | 172.28.0.10/24 | 172.28.0.0/24 |
| srv1 | 172.28.0.11/24 | same L2 (Docker bridge) |

In Docker all the "hosts" are often on **one L2** — ARP is simple; to simulate **two subnets** in lab 15 they use a namespace or a second compose network.

## The route table (intro)

```bash
ip route show
ip route get 8.8.8.8
```

| Route | Behavior |
|---------|-----------|
| `172.28.0.0/24 dev eth0` | connected — directly |
| `default via 172.28.0.1` | everything else to the gateway |
| `10.0.10.0/24 via 10.0.1.5` | static to another subnet |

**Main table** vs **policy routing** — in [chapter 05](05-routing.md).

## ICMP and "ping is not proof"

- A firewall may drop **ICMP** but allow **TCP/443**.
- `ping` succeeds from the **mgmt** VLAN, but the application in the **app** VLAN is unreachable.

For the user's path SLA, test the **same L4** as the client: `curl`, `nc`, a synthetic check.

## Summary

L2 is **who is in one broadcast domain** (ARP, VLAN). L3 is **where to forward** (CIDR, routes). A bad addressing plan costs more than any application bug — it's fixed by migration and downtime.
