# Kubernetes Shorts: Полноценный курс (с нуля)

Цель: сделать из шортсов связный курс, который ведет новичка от терминов до уверенной практики.
Рекомендуемая длительность: **45–75 секунд** (цель ~65–75, когда теме нужна фактура).

Единый CTA (публикация, English voice-over в конце каждого шортса):
`Master Kubernetes faster. Theory, hands-on labs, and interview questions - link in bio.`

Порядок модулей = порядок бота: сначала картина мира → локальный кластер → объекты → kubectl → типичные ошибки → сеть/ресурсы → релизы → хранение → безопасность → наблюдаемость → скейл → Helm/Kustomize/GitOps → CI/CD → платформа → карьера.

Гайд пайплайна: `kubernetes-shorts-pipeline-prompt.md`.

## Модуль 0. Старт и ориентация (1-12)

Формат каждого пункта в этом и всех следующих модулях:
- **Хук:** короткий вопрос/боль новичка по теме урока.
- **Суть:** простое объяснение + 1 практический ориентир (команда/правило/чеклист).
- **CTA:** единая строка выше (не придумывать другой CTA).

1. Что такое Kubernetes за 30 секунд  
   - **Хук:** "Docker уже знаешь, а зачем тогда Kubernetes?"
   - **Суть:** Kubernetes автоматизирует запуск, восстановление и масштабирование контейнеров на кластере.
2. Контейнер vs Pod  
   - **Хук:** "Почему в Kubernetes говорят Pod, а не просто контейнер?"
   - **Суть:** Pod — минимальная сущность запуска; внутри может быть один или несколько контейнеров.
3. Node vs Cluster  
   - **Хук:** "Нода и кластер — это одно и то же?"
   - **Суть:** Cluster — набор нод, Node — отдельный сервер, где реально запускаются Pod.
4. Control Plane простыми словами  
   - **Хук:** "Кто в кластере принимает решения?"
   - **Суть:** Control Plane управляет состоянием кластера и оркестрирует workloads.
5. Worker Node и его роль  
   - **Хук:** "Где фактически работает приложение?"
   - **Суть:** На worker-нодах запускаются контейнеры и исполняются рабочие нагрузки.
6. kubelet: кто запускает Pod на ноде  
   - **Хук:** "Что на ноде следит за Pod?"
   - **Суть:** kubelet применяет инструкции кластера и контролирует состояние Pod локально.
7. API Server: единая точка управления  
   - **Хук:** "Куда уходят все команды `kubectl`?"
   - **Суть:** API Server — центральный вход для операций чтения/изменения ресурсов.
8. etcd: где хранится состояние кластера  
   - **Хук:** "Где хранится 'правда' про кластер?"
   - **Суть:** etcd хранит текущее и желаемое состояние объектов Kubernetes.
9. scheduler: как выбирается нода  
   - **Хук:** "Почему Pod попал именно на эту ноду?"
   - **Суть:** Scheduler выбирает ноду по ресурсам и ограничениям размещения.
10. Desired State: главная идея Kubernetes  
   - **Хук:** "Почему Kubernetes сам исправляет отклонения?"
   - **Суть:** Ты задаешь желаемое состояние, а контроллеры постоянно к нему приводят кластер.
11. Когда Kubernetes *не* нужен  
   - **Хук:** "Все вокруг на k8s — значит, и мне пора?"
   - **Суть:** Для одного сервиса или маленькой команды часто хватает VM/PaaS; k8s окупается при росте сервисов и команд.
12. Миф: «Kubernetes = Docker на стероидах»  
   - **Хук:** "Это же просто оркестратор контейнеров, верно?"
   - **Суть:** Docker запускает контейнер; Kubernetes управляет кластером, сетью, желаемым состоянием и политиками.

## Модуль 1. Локальный старт руками (13-22)

13. Minikube / kind / k3s — что выбрать новичку  
   - **Хук:** "Какой локальный кластер поставить, чтобы не запутаться?"
   - **Суть:** kind — быстрый sandbox в Docker; minikube — удобный локальный UX; k3s — легкий «почти прод».
14. Первый кластер за 5 минут (kind)  
   - **Хук:** "Как получить рабочий Kubernetes без облака?"
   - **Суть:** Подними kind-кластер и сразу проверь `kubectl get nodes`.
15. `kubeconfig` простыми словами  
   - **Хук:** "Что это за файл, без которого `kubectl` молчит?"
   - **Суть:** kubeconfig хранит адреса кластеров, пользователей и contexts для доступа к API.
16. Contexts: переключение между кластерами  
   - **Хук:** "Как работать с несколькими кластерами одной командой?"
   - **Суть:** Context выбирает связку cluster + user + namespace для текущих команд.
17. Как не сломать prod: отдельные contexts  
   - **Хук:** "Как случайно не выкатить в прод?"
   - **Суть:** Держи разные contexts/имена и перед `apply` всегда проверяй `kubectl config current-context`.
18. Image registry: откуда Pod берет образ  
   - **Хук:** "Куда Kubernetes ходит за Docker-образом?"
   - **Суть:** kubelet скачивает образ из registry по имени в `image:`; без доступа к registry Pod не стартует.
19. `ImagePullSecrets`: приватный registry  
   - **Хук:** "Как тянуть образы из закрытого registry?"
   - **Суть:** Secret типа docker-registry и ссылка на него в Pod/ServiceAccount дают доступ к приватным образам.
20. Почему нельзя использовать `latest`  
   - **Хук:** "Почему `latest` ломает предсказуемость релизов?"
   - **Суть:** Невозможно однозначно понять, какая версия реально запущена — фиксируй тег/digest.
21. ImagePullPolicy: когда тянется новый образ  
   - **Хук:** "Почему Pod стартует со старым кодом после деплоя?"
   - **Суть:** Pull policy управляет, когда kubelet скачивает образ заново.
22. Docker Compose → Kubernetes: как переводить головой  
   - **Хук:** "Есть compose-файл — как мыслить в терминах k8s?"
   - **Суть:** service ≈ Deployment+Service, volumes ≈ PVC, env ≈ ConfigMap/Secret.

## Модуль 2. Базовые объекты (23-37)

23. Deployment: правильный способ запускать приложение  
   - **Хук:** "Почему не стоит запускать Pod вручную?"
   - **Суть:** Deployment держит нужное число реплик и управляет безопасными обновлениями.
24. ReplicaSet: что под капотом Deployment  
   - **Хук:** "Кто реально следит за количеством Pod?"
   - **Суть:** ReplicaSet обеспечивает соответствие между желаемым и фактическим числом Pod.
25. StatefulSet: когда нужен для stateful-приложений  
   - **Хук:** "Почему БД часто не деплоят через Deployment?"
   - **Суть:** StatefulSet дает стабильные имена Pod и привязку к постоянному хранилищу.
26. DaemonSet: один Pod на каждую ноду  
   - **Хук:** "Как поставить агент логов на все ноды сразу?"
   - **Суть:** DaemonSet гарантирует запуск одинакового Pod на каждой подходящей ноде.
27. Job: одноразовая задача  
   - **Хук:** "Как запускать миграцию один раз и завершать?"
   - **Суть:** Job выполняет конечную задачу и фиксирует ее успешное/неуспешное завершение.
28. CronJob: задача по расписанию  
   - **Хук:** "Как автоматизировать бэкап каждую ночь?"
   - **Суть:** CronJob по расписанию создает Job и запускает регулярные фоновые процессы.
29. Namespace: как разделять окружения  
   - **Хук:** "Как не смешивать dev и prod в одном кластере?"
   - **Суть:** Namespace логически изолирует ресурсы команд и окружений.
30. Labels: базовая систематизация ресурсов  
   - **Хук:** "На чем в Kubernetes держится группировка объектов?"
   - **Суть:** Labels — ключ/значение метки, по которым сервисы и контроллеры выбирают ресурсы.
31. Selectors: как объекты находят друг друга  
   - **Хук:** "Как Service понимает, к каким Pod направлять трафик?"
   - **Суть:** Selectors отбирают объекты по labels и связывают сущности между собой.
32. Annotations: служебные метаданные  
   - **Хук:** "Куда класть служебную информацию, не влияя на селекторы?"
   - **Суть:** Annotations хранят произвольные метаданные для инструментов и процессов.
33. ConfigMap: внешние конфиги  
   - **Хук:** "Почему конфиги лучше выносить из контейнерного образа?"
   - **Суть:** ConfigMap отделяет настройки от кода и упрощает смену конфигурации.
34. Secret: чувствительные данные  
   - **Хук:** "Где хранить пароли и токены в Kubernetes?"
   - **Суть:** Secret предназначен для чувствительных данных и требует аккуратной политики доступа.
35. ServiceAccount: identity для Pod  
   - **Хук:** "От чьего имени Pod обращается к API кластера?"
   - **Суть:** ServiceAccount задает идентичность workload для RBAC-доступа.
36. Service: стабильная сеть для Pod  
   - **Хук:** "Pod меняются, как дать приложению стабильный адрес?"
   - **Суть:** Service предоставляет постоянный endpoint и балансирует трафик между Pod.
37. Ingress: входящий HTTP/HTTPS-трафик  
   - **Хук:** "Как пустить внешний трафик по доменам и путям?"
   - **Суть:** Ingress описывает правила маршрутизации HTTP/HTTPS к внутренним сервисам.

## Модуль 3. YAML и kubectl-база (38-57)

38. YAML без боли: `apiVersion`, `kind`, `metadata`, `spec`  
   - **Хук:** "Почему ошибка в одном отступе ломает деплой?"
   - **Суть:** Эти 4 блока задают тип ресурса, имя и желаемое состояние объекта.
39. Declarative vs Imperative подход  
   - **Хук:** "Писать YAML или кликать/командовать вручную?"
   - **Суть:** Declarative лучше для повторяемости, imperative полезен для быстрых одноразовых действий.
40. `kubectl get`: первая команда новичка  
   - **Хук:** "С чего начать проверку кластера после входа?"
   - **Суть:** `kubectl get` дает быстрый список объектов и их базовые статусы.
41. `kubectl get all`: почему это не "все"  
   - **Хук:** "Почему часть ресурсов не видна через `get all`?"
   - **Суть:** Команда показывает ограниченный набор, для полного обзора нужны точечные запросы.
42. `kubectl describe`: лучший старт диагностики  
   - **Хук:** "Pod не стартует — куда смотреть первым?"
   - **Суть:** `describe` показывает события, причины ошибок и ключевые параметры ресурса.
43. `kubectl logs` и `--previous`  
   - **Хук:** "Контейнер упал, а текущие логи пустые?"
   - **Суть:** Флаг `--previous` помогает увидеть логи предыдущего запуска контейнера.
44. `kubectl exec`: точечный дебаг внутри контейнера  
   - **Хук:** "Как проверить окружение приложения изнутри?"
   - **Суть:** `exec` дает доступ к контейнеру для короткой диагностики.
45. `kubectl port-forward`: локальный доступ к сервису  
   - **Хук:** "Как протестировать сервис без внешнего ingress?"
   - **Суть:** Port-forward временно прокидывает порт Pod/Service на локальную машину.
46. `kubectl apply` vs `create`  
   - **Хук:** "Почему `create` падает при повторном запуске?"
   - **Суть:** `create` — только создание, `apply` — идемпотентное создание/обновление.
47. `kubectl delete`: что удалять правильно  
   - **Хук:** "Удалил Pod, а он снова появился — почему?"
   - **Суть:** Контроллеры восстанавливают Pod, поэтому обычно удаляют управляющий ресурс.
48. `kubectl edit`: экстренные правки в кластере  
   - **Хук:** "Как быстро исправить ресурс в прод-инциденте?"
   - **Суть:** `edit` удобен для срочного фикса, но изменения нужно вернуть в Git-манифест.
49. `kubectl patch`: точечные изменения  
   - **Хук:** "Нужно сменить одно поле без полного YAML?"
   - **Суть:** `patch` обновляет конкретные части объекта минимальным изменением.
50. `kubectl diff`: посмотреть изменения до применения  
   - **Хук:** "Как заранее увидеть, что поменяется в кластере?"
   - **Суть:** `diff` сравнивает манифест с текущим состоянием до `apply`.
51. `kubectl explain`: документация прямо в CLI  
   - **Хук:** "Забыл поле в `spec` и не хочешь искать в браузере?"
   - **Суть:** `explain` показывает структуру и описание полей ресурса.
52. `kubectl api-resources`: какие ресурсы доступны  
   - **Хук:** "Как узнать, какие типы объектов поддерживает кластер?"
   - **Суть:** Команда выводит список API-ресурсов и их shortnames.
53. `kubectl get -o wide`: расширенный обзор  
   - **Хук:** "Нужно быстро увидеть node/IP/доп.поля?"
   - **Суть:** `-o wide` добавляет практичные поля для оперативной диагностики.
54. `kubectl get pods -A`: поиск по всем namespace  
   - **Хук:** "Не видишь Pod — может, он не в том namespace?"
   - **Суть:** Флаг `-A` показывает ресурсы кластера сразу во всех namespace.
55. `kubectl cp`: копирование файлов из/в Pod  
   - **Хук:** "Как достать лог-файл или конфиг из контейнера?"
   - **Суть:** `kubectl cp` копирует файлы между локальной машиной и Pod.
56. `kubectl wait`: ожидания в автоматизации  
   - **Хук:** "Как не писать циклы ожидания в CI-скриптах?"
   - **Суть:** `wait` блокирует выполнение до нужного состояния ресурса.
57. Мини-рутина: 5 команд каждое утро  
   - **Хук:** "С чего начинать день дежурному по кластеру?"
   - **Суть:** Быстрый ежедневный чек по Pod, Service, событиям, ресурсам и rollout-статусу.

## Модуль 4. Статусы и ошибки, которые все гуглят (58-72)

58. Как читать колонку `STATUS` у Pod  
   - **Хук:** "Что значат Running, Pending, CrashLoopBackOff?"
   - **Суть:** STATUS — краткий итог фазы/условия Pod; детали всегда в `describe` и Events.
59. `ContainerCreating` vs `Pending`  
   - **Хук:** "Pod не Running — это уже ошибка?"
   - **Суть:** Pending — еще не назначен/не готов к старту; ContainerCreating — уже на ноде, идет создание контейнера.
60. `ErrImagePull` / `ImagePullBackOff`  
   - **Хук:** "Почему образ не скачивается?"
   - **Суть:** Проверь имя/тег, registry, сеть ноды и ImagePullSecrets.
61. `CreateContainerConfigError`  
   - **Хук:** "Pod даже не стартует контейнер — что сломано?"
   - **Суть:** Часто нет ConfigMap/Secret, на который ссылается манифест.
62. `CrashLoopBackOff` vs просто `Error`  
   - **Хук:** "Почему одно падение — Error, а другое — CrashLoop?"
   - **Суть:** CrashLoop — повторные рестарты с backoff; Error — контейнер завершился с ошибкой в текущем цикле.
63. `RunContainerError`  
   - **Хук:** "Образ скачался, а контейнер не запустился?"
   - **Суть:** Смотри команду старта, volume mounts и права на файловую систему.
64. `Completed` у Job — это норма  
   - **Хук:** "Job в Completed — он сломался?"
   - **Суть:** Для Job Completed значит задача успешно закончилась.
65. Почему `RESTARTS` растет  
   - **Хук:** "Рестарты увеличиваются, а статус Running — что делать?"
   - **Суть:** Смотри liveness, OOM, падения процесса и `logs --previous`.
66. Events vs Logs: куда смотреть первым  
   - **Хук:** "Логи пустые — значит, проблемы нет?"
   - **Суть:** Events объясняют оркестрацию; logs — поведение приложения внутри контейнера.
67. `kubectl get events --sort-by=.lastTimestamp`  
   - **Хук:** "Как увидеть свежие события, а не кашу?"
   - **Суть:** Сортировка по времени показывает последние причины сбоев первыми.
68. `kubectl top pods/nodes` и Metrics Server  
   - **Хук:** "Как увидеть CPU/память прямо в CLI?"
   - **Суть:** `kubectl top` работает, если в кластере установлен Metrics Server.
69. `kubectl debug` / ephemeral containers  
   - **Хук:** "В образе нет shell — как дебажить?"
   - **Суть:** Ephemeral container временно добавляет debug-инструменты к живому Pod.
70. Разбор: почему Pod в Pending (live-формат)  
   - **Хук:** "Застрял в Pending — с чего начать разбор?"
   - **Суть:** Ресурсы нод → taints/tolerations → PVC → affinity → Events.
71. Разбор: Service без endpoints (live-формат)  
   - **Хук:** "Service есть, а endpoints пустые — почему?"
   - **Суть:** Не совпадают labels/selectors, Pod не Ready или в другом namespace.
72. Чеклист: 60 секунд на инцидент  
   - **Хук:** "Сервис лежит — какие 4 команды сразу?"
   - **Суть:** `get/describe` → Events → logs/--previous → endpoints/rollout.

## Модуль 5. Порты, env и тома без путаницы (73-84)

73. `containerPort` ≠ `Service.port` ≠ `targetPort`  
   - **Хук:** "Какой порт куда прописывать — вечная путаница?"
   - **Суть:** containerPort — в контейнере, port — у Service, targetPort — куда реально слать на Pod.
74. Env в Pod: `env` vs `envFrom`  
   - **Хук:** "Когда перечислять переменные, а когда подключать целиком?"
   - **Суть:** `env` — точечно; `envFrom` — сразу весь ConfigMap/Secret как набор переменных.
75. ConfigMap как файл vs как переменные  
   - **Хук:** "Монтировать конфиг или класть в env?"
   - **Суть:** Env удобен для флагов; volume mount — для файлов и больших конфигов.
76. Secret mount vs env: что безопаснее на практике  
   - **Хук:** "Секрет в env — это ок?"
   - **Суть:** Mount обычно предпочтительнее: меньше утечек через process list и проще ротация файлом.
77. `subPath`: удобно и опасно  
   - **Хук:** "Почему иногда монтируют один файл через subPath?"
   - **Суть:** subPath монтирует отдельный файл, но обновления ConfigMap/Secret могут не подхватываться.
78. Projected volumes одной картинкой  
   - **Хук:** "Можно ли склеить несколько источников в один том?"
   - **Суть:** Projected volume объединяет Secret/ConfigMap/DownwardAPI в одну директорию.
79. Downward API: Pod узнает о себе сам  
   - **Хук:** "Как приложению узнать свое имя, namespace, лимиты?"
   - **Суть:** Downward API прокидывает метаданные Pod в env или файлы без хардкода.
80. Multi-container Pod: общение через `localhost`  
   - **Хук:** "Два контейнера в одном Pod — как они ходят друг к другу?"
   - **Суть:** У контейнеров одного Pod общая сеть, поэтому доступ по localhost и общим портам.
81. Shared volume между app и sidecar  
   - **Хук:** "Как sidecar читает файлы основного приложения?"
   - **Суть:** Общий volume (часто emptyDir) — стандартный канал обмена данными внутри Pod.
82. `readOnlyRootFilesystem`: зачем  
   - **Хук:** "Почему корень файловой системы делают read-only?"
   - **Суть:** Усложняет запись вредоносом и заставляет явно выделять writable-тома под нужды приложения.
83. `securityContext`: runAsNonRoot за 30 сек  
   - **Хук:** "Зачем запрещать запуск от root?"
   - **Суть:** non-root снижает ущерб при компрометации контейнера — базовая гигиена Pod.
84. Capabilities: зачем дропать `ALL`  
   - **Хук:** "Что такое Linux capabilities у контейнера?"

## Модуль 6. Сеть без магии (85-110)

85. Service types: ClusterIP, NodePort, LoadBalancer  
   - **Хук:** "Как понять, какой тип Service выбрать?"
   - **Суть:** ClusterIP — внутри кластера, NodePort — доступ через ноды, LoadBalancer — внешний балансировщик.
86. Почему Service не видит Pod (labels/selectors)  
   - **Хук:** "Service создан, а трафик не идет — в чем подвох?"
   - **Суть:** Чаще всего не совпадают labels Pod и selectors Service.
87. EndpointSlice: где хранится список endpoints  
   - **Хук:** "Откуда Service знает IP нужных Pod?"
   - **Суть:** EndpointSlice хранит актуальные адреса backend-Pod для маршрутизации.
88. DNS в Kubernetes: как сервисы находят друг друга  
   - **Хук:** "Почему можно ходить на `my-service` без IP?"
   - **Суть:** Встроенный DNS резолвит имена сервисов в адреса внутри кластера.
89. FQDN сервиса между namespace  
   - **Хук:** "Когда короткого имени сервиса уже недостаточно?"
   - **Суть:** Для явной адресации между namespace используй полное DNS-имя сервиса.
90. Ingress vs Service: где чей слой  
   - **Хук:** "Ingress и Service делают одно и то же?"
   - **Суть:** Service соединяет внутреннюю сеть, Ingress управляет внешним HTTP/HTTPS входом.
91. Ingress Controller: почему Ingress "сам не работает"  
   - **Хук:** "Создал Ingress, но маршрутизации нет — почему?"
   - **Суть:** Нужен установленный Ingress Controller, который применяет правила Ingress.
92. Session Affinity: закрепление клиента за Pod  
   - **Хук:** "Как сделать 'липкую' сессию в сервисе?"
   - **Суть:** Session Affinity направляет повторные запросы клиента в тот же Pod.
93. `externalTrafficPolicy`: Local vs Cluster  
   - **Хук:** "Почему теряется source IP клиента?"
   - **Суть:** Режим Local помогает сохранить client IP, Cluster — шире балансирует по нодам.
94. Headless Service: зачем без балансировки  
   - **Хук:** "Зачем Service без виртуального IP?"
   - **Суть:** Headless Service возвращает DNS-записи отдельных Pod для stateful-сценариев.
95. Stateful DNS для StatefulSet  
   - **Хук:** "Как у stateful Pod появляются стабильные DNS-имена?"
   - **Суть:** StatefulSet + Headless Service дают предсказуемые имена для каждого Pod.
96. NodePort для dev/test сценариев  
   - **Хук:** "Как быстро открыть сервис снаружи без Ingress?"
   - **Суть:** NodePort удобен для теста, но обычно не лучший финальный вариант для прода.
97. Базовый путь запроса: пользователь -> Ingress -> Service -> Pod  
   - **Хук:** "Куда реально идет запрос после открытия сайта?"
   - **Суть:** Трафик проходит через уровни маршрутизации до конкретного Pod-бэкенда.
98. Проверка доступности сервиса после деплоя  
   - **Хук:** "Как быстро понять, что сервис реально жив?"
   - **Суть:** Проверяй endpoints, readiness Pod и фактический ответ приложения.
99. Частые сетевые ошибки новичка  
   - **Хук:** "Почему сеть ломается в самых базовых кейсах?"
   - **Суть:** Ошибки в портах, selectors, namespace и ingress-правилах — топ причин.
100. Мини-чеклист сетевой диагностики  
   - **Хук:** "С чего идти по шагам, когда 'нет доступа'?"
   - **Суть:** Service -> Endpoints -> Pod status -> Logs -> Ingress -> DNS.
101. Что мониторить в сети первым делом  
   - **Хук:** "Какие метрики сети реально важны на старте?"
   - **Суть:** Ошибки, задержка, доступность endpoints и насыщение по трафику.
102. Gateway API vs Ingress  
   - **Хук:** "Ingress устарел — теперь всем нужен Gateway API?"
   - **Суть:** Gateway API — более выразительная модель входа; Ingress все еще массово используется.
103. TLS на Ingress: сертификат за минуту (концепт)  
   - **Хук:** "Как включить HTTPS на входном трафике?"
   - **Суть:** Ingress ссылается на TLS Secret с сертификатом и ключом для нужного хоста.
104. cert-manager: кто обновляет сертификаты  
   - **Хук:** "Кто следит, чтобы TLS не протух?"
   - **Суть:** cert-manager выпускает и продлевает сертификаты по манифестам в кластере.
105. HTTP → HTTPS redirect  
   - **Хук:** "Как принудительно увести пользователей на HTTPS?"
   - **Суть:** Настраивается на уровне Ingress Controller/Gateway правилом редиректа.
106. Path-based vs host-based routing  
   - **Хук:** "Когда делить по домену, а когда по пути?"
   - **Суть:** Host — разные приложения/бренды; path — разные части одного домена.
107. Почему 502/504 часто не «в приложении»  
   - **Хук:** "Сайт отдает 502 — сразу лезть в код?"
   - **Суть:** Сначала проверь upstream readiness, Service/endpoints и таймауты Ingress.
108. Health checks снаружи vs readiness внутри  
   - **Хук:** "Внешний мониторинг зеленый, а трафик уже сыпется?"
   - **Суть:** Внешний probe ≠ readiness: смотри оба слоя, иначе ловишь ложное спокойствие.
109. WAF/CDN перед кластером — где граница  
   - **Хук:** "Защита начинается в Kubernetes или раньше?"
   - **Суть:** CDN/WAF режут внешние угрозы; NetworkPolicy и RBAC — уже внутри кластера.
110. Canary через Ingress/Gateway (идея)  
   - **Хук:** "Как пустить 5% трафика на новую версию?"
   - **Суть:** Правила весов/заголовков на входе постепенно сдвигают долю трафика на canary.

## Модуль 7. Ресурсы и стабильность Pod (111-128)

111. Requests и Limits: основа стабильности  
   - **Хук:** "Почему без лимитов кластер начинает 'плыть'?"
   - **Суть:** Requests резервируют ресурсы, limits ограничивают пик потребления контейнера.
112. QoS: BestEffort, Burstable, Guaranteed  
   - **Хук:** "Какие Pod пострадают первыми при нехватке ресурсов?"
   - **Суть:** QoS-класс влияет на приоритет выживания Pod под давлением ноды.
113. OOMKilled: что это и как чинить  
   - **Хук:** "Контейнер падает без явной ошибки в коде?"
   - **Суть:** OOMKilled значит превышен лимит памяти; нужно пересмотреть limits и профиль памяти.
114. Evicted Pod: почему выселяют  
   - **Хук:** "Pod внезапно исчез — это баг или политика кластера?"
   - **Суть:** Eviction происходит при дефиците памяти/диска на ноде и защите стабильности кластера.
115. Pending Pod: частые причины  
   - **Хук:** "Почему Pod застрял в Pending и не стартует?"
   - **Суть:** Обычно не хватает ресурсов, есть taint-ограничения или проблемы с PVC.
116. Liveness probe: "жив ли процесс"  
   - **Хук:** "Как понять, что контейнер завис и его нужно перезапустить?"
   - **Суть:** Liveness проверка выявляет 'мертвые' процессы и инициирует рестарт Pod.
117. Readiness probe: "готов ли к трафику"  
   - **Хук:** "Почему сервис шлет трафик в еще не готовый Pod?"
   - **Суть:** Readiness отсеивает неподготовленные Pod от балансировки Service.
118. Startup probe: для долгого старта  
   - **Хук:** "Приложение долго поднимается и падает раньше времени?"
   - **Суть:** Startup probe дает окну старта время, не провоцируя преждевременный рестарт.
119. CrashLoopBackOff: быстрый алгоритм поиска причины  
   - **Хук:** "Pod уходит в бесконечные рестарты — что делать первым?"
   - **Суть:** Проверяй `describe`, `logs --previous`, конфиг/секреты и команду запуска.
120. Graceful shutdown и `terminationGracePeriodSeconds`  
   - **Хук:** "Как выключать Pod без потери запросов?"
   - **Суть:** Корректный grace period дает приложению завершить работу и сбросить соединения.
121. Почему Pod зависает в Terminating  
   - **Хук:** "Удалил Pod, а он не исчезает долгое время?"
   - **Суть:** Причины — finalizers, долгий shutdown-hook или проблемы с томами.
122. Init Containers: подготовка перед стартом  
   - **Хук:** "Как прогонять проверки до запуска основного контейнера?"
   - **Суть:** Init-контейнеры выполняются по очереди и подготавливают окружение приложения.
123. Sidecar-паттерн для вспомогательных задач  
   - **Хук:** "Зачем рядом с приложением второй контейнер?"
   - **Суть:** Sidecar выносит служебные функции: прокси, логирование, синхронизацию.
124. EmptyDir для временных данных  
   - **Хук:** "Где хранить временные файлы внутри Pod?"
   - **Суть:** EmptyDir живет пока жив Pod и подходит для кэша/временных артефактов.
125. PodDisruptionBudget: защита доступности  
   - **Хук:** "Как не потерять сервис при обслуживании нод?"
   - **Суть:** PDB ограничивает допустимое число одновременно недоступных реплик.
126. PriorityClass: кого спасать первым  
   - **Хук:** "Какие Pod должны выживать при дефиците?"
   - **Суть:** PriorityClass задает приоритет для критичных workloads в борьбе за ресурсы.
127. ResourceQuota: лимиты на namespace  
   - **Хук:** "Как одна команда может случайно 'съесть' весь кластер?"
   - **Суть:** ResourceQuota ограничивает суммарные ресурсы и количество объектов в namespace.
128. LimitRange: стандарты requests/limits  
   - **Хук:** "Как заставить всех задавать ресурсы единообразно?"
   - **Суть:** LimitRange задает минимумы, максимумы и дефолты ресурсов для Pod/контейнеров.

## Модуль 8. Планирование и размещение (129-140)

129. Taints: запрет размещения на ноде  
   - **Хук:** "Как запретить обычным Pod запускаться на отдельной ноде?"
   - **Суть:** Taint помечает ноду как ограниченную для Pod без соответствующих tolerations.
130. Tolerations: осознанное исключение  
   - **Хук:** "Как разрешить конкретному Pod обойти taint?"
   - **Суть:** Toleration позволяет Pod запускаться на tainted-ноде по заданным правилам.
131. Affinity: размещаем рядом  
   - **Хук:** "Как сказать scheduler: запускай рядом с нужными сервисами?"
   - **Суть:** Affinity управляет предпочтительным/обязательным размещением Pod по меткам.
132. Anti-affinity: разводим по нодам  
   - **Хук:** "Как не класть все реплики на один сервер?"
   - **Суть:** Anti-affinity распределяет реплики по разным нодам для отказоустойчивости.
133. Topology spread constraints: равномерность по зонам  
   - **Хук:** "Почему все Pod могут оказаться в одной зоне?"
   - **Суть:** Spread constraints обеспечивают более равномерное распределение между доменами топологии.
134. Cordon: отключить ноду от новых Pod  
   - **Хук:** "Как подготовить ноду к обслуживанию без новых нагрузок?"
   - **Суть:** Cordon делает ноду unschedulable, но не трогает уже запущенные Pod.
135. Drain: безопасно освободить ноду  
   - **Хук:** "Как корректно вывести ноду из эксплуатации?"
   - **Суть:** Drain эвакуирует Pod с ноды с учетом контроллеров и ограничений доступности.
136. Обслуживание ноды без даунтайма  
   - **Хук:** "Можно ли обновлять ноды и не ронять сервис?"
   - **Суть:** Комбинируй PDB, cordon/drain и поэтапное обслуживание нод.
137. Почему Pod оказался именно на этой ноде  
   - **Хук:** "Как объяснить решение scheduler в конкретном кейсе?"
   - **Суть:** Смотри ресурсы, taints/tolerations, affinity и события назначения.
138. Размещение критичных и некритичных сервисов  
   - **Хук:** "Как защитить важные сервисы при дефиците ресурсов?"
   - **Суть:** Разделяй нагрузки по приоритетам и нодам, задавая policy размещения.
139. DaemonSet + tolerations: частый кейс  
   - **Хук:** "Почему агент мониторинга не запускается на всех нодах?"
   - **Суть:** Для tainted-нод часто нужны tolerations в DaemonSet-манифесте.
140. Мини-чеклист по планированию  
   - **Хук:** "Что проверить перед запуском новой нагрузки?"
   - **Суть:** Ресурсы, ограничения размещения, отказоустойчивость и правила эвакуации.

## Модуль 9. Релизы и откаты (141-158)

141. Rolling Update: обновление без даунтайма  
   - **Хук:** "Как выпускать новую версию без полной остановки?"
   - **Суть:** Rolling Update обновляет Pod постепенно, сохраняя доступность сервиса.
142. `kubectl rollout status`: контроль релиза  
   - **Хук:** "Как понять, что релиз еще идет или уже сломался?"
   - **Суть:** Команда показывает текущее состояние rollout и прогресс обновления.

   - **Хук:** "Как узнать, на что откатываться после неудачного апдейта?"
   - **Суть:** История ревизий помогает выбрать стабильную точку возврата.
144. `kubectl rollout undo`: быстрый rollback  
   - **Хук:** "Релиз сломал прод, как откатиться за минуты?"

145. `kubectl set image`: быстрый update образа  
   - **Хук:** "Как быстро сменить версию приложения без правки файла?"
   - **Суть:** Set image обновляет контейнерный образ и запускает новый rollout.
146. `rollout restart`: перезапуск по-взрослому  
   - **Хук:** "Как перезапустить deployment без ручного удаления Pod?"
   - **Суть:** Rollout restart запускает контролируемое пересоздание Pod.
147. Почему `kubectl delete pod` не равно релизу  
   - **Хук:** "Можно ли обновлять приложение удалением Pod?"
   - **Суть:** Это аварийная мера, а не управляемый релизный процесс.
148. `revisionHistoryLimit`: баланс истории и чистоты  
   - **Хук:** "Зачем ограничивать количество старых ревизий?"
   - **Суть:** Параметр контролирует объем истории rollback и чистоту ресурсов.
149. Blue/Green vs Rolling vs Canary  
   - **Хук:** "Какой стратегии релиза достаточно на старте?"

150. Smoke test после деплоя  
   - **Хук:** "Почему 'деплой зеленый' не гарантирует, что сервис работает?"
   - **Суть:** Мини-тест после rollout подтверждает критичный пользовательский путь.
151. Чеклист "до deploy"  
   - **Хук:** "Что проверить, чтобы не катить 'вслепую'?"
   - **Суть:** Версия образа, конфиги/секреты, ресурсы, миграции и план отката.
152. Чеклист "после deploy"  
   - **Хук:** "На что смотреть в первые минуты после релиза?"
   - **Суть:** Rollout, ошибки, latency, readiness и smoke-проверки.
153. Мини-runbook инцидента  
   - **Хук:** "Сервис упал: какие 5 шагов сделать сразу?"
   - **Суть:** Фиксируем симптомы, проверяем rollout/events/logs и запускаем rollback при необходимости.
154. Топ ошибок при первом релизе  
   - **Хук:** "Почему новички часто ломают первый прод-деплой?"
   - **Суть:** Часто забывают probes, ресурсы, наблюдаемость и rollback-процедуру.
155. Как не деплоить "не в тот кластер" (kube context)  
   - **Хук:** "Как случайно не выкатить dev в prod?"
   - **Суть:** Всегда проверяй текущий context/namespace перед применением изменений.
156. Progressive delivery на базовом уровне  
   - **Хук:** "Как выкатывать осторожно, а не сразу на всех?"
   - **Суть:** Поэтапно увеличивай долю трафика/реплик после проверки сигналов качества.
157. Пост-деплой smoke + health-check  
   - **Хук:** "Как быстро проверить, что релиз реально рабочий?"
   - **Суть:** Выполняй минимальный пользовательский сценарий и проверяй probes/метрики.
158. Миф: «больше реплик = всегда лучше»  
   - **Хук:** "Накинул реплик — и производительность выросла?"
   - **Суть:** Без готовности БД/лимитов/очередей лишние реплики усиливают bottleneck.

   - **Хук:** "Как сделать разовый бэкап базы в Kubernetes?"

## Модуль 11. Безопасность для новичка (173-192)

173. RBAC: модель прав в Kubernetes  
   - **Хук:** "Почему команда получает `forbidden` даже при доступе к кластеру?"

174. Role vs ClusterRole  
   - **Хук:** "Когда Role недостаточно и нужен ClusterRole?"

175. RoleBinding vs ClusterRoleBinding  
   - **Хук:** "Права созданы, но не работают — что забыли?"
   - **Суть:** Binding связывает роль с пользователем/группой/ServiceAccount.
176. `kubectl auth can-i`: быстрая проверка доступа  
   - **Хук:** "Как заранее проверить право на действие?"
   - **Суть:** Команда быстро валидирует RBAC-доступ до выполнения операции.
177. ServiceAccount best practices  
   - **Хук:** "Почему плохо запускать все Pod на default ServiceAccount?"
   - **Суть:** Лучше выделять отдельные ServiceAccount с минимально нужными правами.
178. Secret: почему base64 не шифрование  
   - **Хук:** "Секрет в base64 — это действительно безопасно?"
   - **Суть:** Base64 — кодирование, безопасность дает контроль доступа и шифрование на уровне хранилища.
179. Безопасная ротация секретов (база)  
   - **Хук:** "Как менять токены без простоя сервиса?"
   - **Суть:** Ротация требует обновления секрета, пересоздания Pod и контроля готовности.
180. ConfigMap и Secret: что куда класть  
   - **Хук:** "Где граница между обычной настройкой и секретом?"
   - **Суть:** Публичные конфиги — в ConfigMap, чувствительные данные — в Secret.
181. NetworkPolicy: ограничение east-west трафика  
   - **Хук:** "Как запретить лишние соединения между Pod?"
   - **Суть:** NetworkPolicy задает явные правила, кто и куда может подключаться внутри кластера.
182. Минимальные права вместо admin  
   - **Хук:** "Почему `cluster-admin` почти всегда плохая идея?"
   - **Суть:** Принцип least privilege снижает риск ошибок и компрометации.
183. Ошибки RBAC, которые делают все  
   - **Хук:** "Какие RBAC-ошибки чаще всего ломают безопасность?"
   - **Суть:** Широкие wildcard-права и общие аккаунты без изоляции.
184. Pod Security Standards: Privileged / Baseline / Restricted  
   - **Хук:** "Как быстро понять 'насколько опасен' Pod?"
   - **Суть:** PSS задает уровни ограничений на привилегии контейнеров и хоста.
185. Admission controllers / webhooks (концепт)  
   - **Хук:** "Кто может отклонить мой YAML еще до запуска?"
   - **Суть:** Admission-слой валидирует и мутирует объекты при создании/обновлении.
186. Policy-as-code идея (Kyverno/OPA — обзор)  
   - **Хук:** "Как запретить опасные манифесты автоматически?"
   - **Суть:** Политики в коде проверяют манифесты в CI и/или на входе в API.
187. Базовая модель threat thinking для k8s  
   - **Хук:** "С чего начать думать о рисках в кластере?"
   - **Суть:** Определи активы, потенциальные векторы атаки и минимальные защитные меры.
188. Миф: «Namespace = изоляция безопасности»  
   - **Хук:** "Namespace защищает команды друг от друга?"
   - **Суть:** Это логическая граница; без RBAC/NetworkPolicy реальной изоляции мало.
189. Миф: «Secret в k8s = сейф»  
   - **Хук:** "Положил в Secret — и можно не бояться?"
   - **Суть:** Нужны RBAC, шифрование etcd, ротация и минимизация доступа к секретам.
190. Чеклист безопасности перед релизом  
   - **Хук:** "Что проверить до выкатки, чтобы не открыть дыру?"
   - **Суть:** Права, секреты, сетевые правила, образы и критичные настройки Pod.
191. Чеклист безопасности после инцидента  
   - **Хук:** "Инцидент закрыт, а что делать дальше?"
   - **Суть:** Ротация секретов, ревизия прав, фиксация уроков и обновление runbook.
192. Multi-tenancy: namespace как граница  
   - **Хук:** "Как делить кластер между командами на старте?"
   - **Суть:** Namespace + RBAC + квоты — минимальная модель совместного использования.

   - **Хук:** "Какие метрики покрывают базовое здоровье сервиса?"

   - **Хук:** "Нагрузка резко выросла — что можно сделать прямо сейчас?"

   - **Хук:** "Как автоматом добавлять Pod при росте нагрузки?"

   - **Хук:** "CPU низкий, а очередь растет — как скейлить правильно?"
   - **Суть:** Для таких кейсов нужен HPA по бизнес-метрикам (например, длине очереди).
208. VPA: автоподбор ресурсов Pod  
   - **Хук:** "Как перестать гадать с requests/limits вручную?"
   - **Суть:** VPA анализирует потребление и рекомендует/применяет новые размеры ресурсов.

   - **Хук:** "Скейлить реплики или размер контейнера?"

   - **Хук:** "Как заметить проблему до аварии?"
   - **Суть:** Смотри загрузку CPU/memory/IO и throttling как ранние сигналы деградации.
211. Bottleneck на уровне приложения vs инфраструктуры  
   - **Хук:** "Проблема в коде или в кластере — как отличить?"
   - **Суть:** Сравни метрики приложения и нод, чтобы локализовать источник узкого места.
212. Топ причин деградации производительности  
   - **Хук:** "Почему сервис внезапно стал медленным?"
   - **Суть:** Часто виноваты лимиты ресурсов, внешние зависимости, плохие запросы и очереди.
213. Чеклист оптимизации под нагрузку  
   - **Хук:** "С чего начать ускорение сервиса системно?"
   - **Суть:** Иди по шагам: метрики -> гипотеза -> изменение -> валидация -> откат при необходимости.
214. Миф: «без Limits безопаснее»  
   - **Хук:** "Если не ставить limits, Pod точно не убьют?"
   - **Суть:** Без limits один Pod может съесть ноду; limits защищают соседей и кластер.
215. SLO/SLA простыми словами  
   - **Хук:** "Как договориться, что значит 'сервис работает хорошо'?"
   - **Суть:** SLO задает внутреннюю цель надежности, SLA — внешние обязательства перед клиентом.
216. Runbook: как фиксировать знания команды  
   - **Хук:** "Как не решать один и тот же инцидент каждый раз с нуля?"
   - **Суть:** Runbook фиксирует шаги диагностики и восстановления для повторяемых ситуаций.
217. Postmortem для новичков: без обвинений  
   - **Хук:** "Как разбирать инциденты, чтобы команда росла?"
   - **Суть:** Фокус на причинах в системе и процессах, а не на поиске виноватых.
218. Чеклист дежурства: что смотреть каждый час  
   - **Хук:** "Дежуришь впервые — на что глазеть?"

## Модуль 14. Helm и повторяемые релизы (219-230)

219. Helm: зачем нужен поверх YAML  
   - **Хук:** "Надоело копировать десятки YAML между проектами?"
   - **Суть:** Helm шаблонизирует манифесты и делает релизы повторяемыми.
220. Что такое chart и release  
   - **Хук:** "Chart и release — в чем разница?"
   - **Суть:** Chart — шаблон приложения, release — конкретно установленный экземпляр в кластере.
221. Структура chart: `templates`, `values`, `Chart.yaml`  
   - **Хук:** "Что за файлы в Helm-чарте и за что они отвечают?"
   - **Суть:** Templates генерируют манифесты, values задают параметры, Chart.yaml описывает пакет.
222. `values.yaml`: управление окружениями  
   - **Хук:** "Как одним chart деплоить dev и prod?"
   - **Суть:** Меняй values-файлы по окружениям без переписывания шаблонов.
223. `helm install`: первый релиз  
   - **Хук:** "Как запустить приложение через Helm одной командой?"
   - **Суть:** Install создает release из chart с заданными значениями.
224. `helm upgrade`: обновления  
   - **Хук:** "Как безопасно обновить chart или конфиг?"
   - **Суть:** Upgrade применяет новую ревизию release с историей изменений.
225. `helm rollback`: откат  
   - **Хук:** "Как быстро вернуться к рабочей версии после неудачного апдейта?"
   - **Суть:** Rollback восстанавливает предыдущую ревизию release.
226. `helm history`: ревизии релиза  
   - **Хук:** "Как узнать, какие версии уже выкатывались?"
   - **Суть:** History показывает список ревизий и их статусы для анализа и отката.
227. Переменные окружений через values  
   - **Хук:** "Как удобно параметризовать образы, порты и флаги?"
   - **Суть:** Используй values для централизованной настройки env-переменных и параметров deployment.
228. Частые ошибки в templating  
   - **Хук:** "Почему chart рендерится не так, как ожидалось?"
   - **Суть:** Ошибки в именах ключей, отступах и условных блоках ломают итоговый YAML.
229. Helm + CI/CD базовый сценарий  
   - **Хук:** "Как встроить Helm в автоматический pipeline?"
   - **Суть:** Pipeline собирает образ, обновляет values и делает контролируемый `helm upgrade`.
230. Чеклист "chart готов к проду"  
   - **Хук:** "Когда можно считать chart production-ready?"
   - **Суть:** Нужны валидация values, ресурсы, probes, rollback-план и документация.

   - **Хук:** "Как применить kustomize без лишних инструментов?"

235. Patches без копипасты манифестов  
   - **Хук:** "Нужно поменять только image и replicas?"

236. ConfigMapGenerator / SecretGenerator  
   - **Хук:** "Как не руками создавать ConfigMap при каждом изменении файла?"

237. Почему руками править прод — плохо  
   - **Хук:** "Сделал `kubectl edit` в проде — и что дальше?"

238. Drift: кластер уехал от Git  
   - **Хук:** "Как понять, что в кластере уже не то, что в репозитории?"

239. Argo CD / Flux — идея GitOps одной картинкой  
   - **Хук:** "Кто применяет манифесты, если не человек?"
   - **Суть:** GitOps-агент синхронизирует желаемое состояние из Git в кластер.
240. PR → sync → cluster  
   - **Хук:** "Как выглядит рабочий день в GitOps?"
   - **Суть:** Изменение через Pull Request, merge, автоматический sync и проверка здоровья.

## Модуль 16. CI/CD и поставка в кластер (241-248)

   - **Суть:** Учись по спринтам: теория, практика в sandbox, мини-проекты и разбор инцидентов.
256. Топ-10 вопросов на k8s junior interview  
   - **Хук:** "Что чаще всего спрашивают на собесе?"
   - **Суть:** Pod/Deployment/Service, probes, requests/limits, сеть, RBAC и разбор Pending/CrashLoop.

## Модуль 18. Разборы «на собесе» и закрепление (259-266)

259. «Что будет, если убить kubelet?»  
   - **Хук:** "Любимый каверзный вопрос интервьюера"
   - **Суть:** Новые Pod на ноде не появятся корректно; уже бегущие контейнеры могут жить, но контроль состояния ломается.
260. «Чем Service отличается от Ingress?»  
   - **Хук:** "Один вопрос — и сразу видно уровень"
   - **Суть:** Service — стабильный доступ к Pod внутри/на входе L4; Ingress — HTTP-маршрутизация снаружи.
261. «Requests vs Limits» — идеальный ответ  
   - **Хук:** "Как ответить коротко и правильно?"
   - **Суть:** Requests — резерв для scheduler; Limits — потолок runtime; от них же зависит QoS.
262. Миф-сводка: 5 опасных упрощений новичка  
   - **Хук:** "Какие убеждения чаще всего подводят в проде?"
   - **Суть:** latest безопасен; namespace = security; Secret = сейф; без limits лучше; больше реплик всегда спасает.
263. Чеклист: я готов к junior-роли  
   - **Хук:** "Как понять, что базы уже хватает?"
   - **Суть:** Можешь задеплоить сервис, объяснить сеть, починить Pending/CrashLoop и откатить релиз.
264. Мини-проект: одно приложение end-to-end  
   - **Хук:** "Чем закрепить весь курс?"
   - **Суть:** Deployment + Service + Ingress + Config/Secret + probes + HPA + пайплайн.
265. Мини-проект: сломай и почини  
   - **Хук:** "Как тренировать диагностику?"
   - **Суть:** Намеренно ломай selectors/ports/secrets и восстанавливай по чеклисту.
266. Что дальше после курса  
   - **Хук:** "Куда идти, когда шортсы закончились?"
   - **Суть:** Свой sandbox-кластер, разбор инцидентов, CKA-траектория и вклад в платформенные задачи команды.

## Как публиковать, чтобы досматривали

- Выпускай модулями (сериями), а не вразнобой  
- В конце каждого видео анонсируй следующий урок  
- Держи единый визуальный стиль и рубрикатор модуля  
- Повторяй ключевые команды на экране крупно  
- Делай 1-2 "диагностических" шортса на каждые 5 теоретических  
- Не прыгай через модули: локальный кластер → объекты → kubectl → ошибки → сеть → дальше по списку
